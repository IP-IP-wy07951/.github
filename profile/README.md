<h2>多 IP 专线的配置，核心是「不让地址打架」</h2>
<p>一条专线上挂多个公网地址，技术上不难，难的是让它们互不干扰。常见的失败不是配不上，而是配上了却时通时不通：请求从一个地址出去，响应从另一个地址回来，连接就建立不起来。这类问题排查起来很费时间，因为它不像「完全不通」那么明确。</p>
<p>下面按「接口、路由、转换、验证」四层讲，每层给出容易出错的点。</p>

<h2>第一层：接口与地址绑定</h2>
<p>把多个地址绑在同一接口上，或分绑在多个接口上。两种做法各有适用：单接口多地址便于统一管理，多接口更适合需要物理分离的场景。</p>
<p>容易出错的点是掩码。多地址场景下，掩码决定了每段地址的可用范围，填错会导致部分地址无法使用，而配置页看起来毫无异常。</p>

<p>第二行是多地址场景的核心。若响应从错误的地址返回，对端会认为连接不属于自己，直接丢弃。症状是「发出去了但没回音」。</p>

<h2>第三层：地址转换</h2>
<p>内网设备要出网，需要转换。两种常见做法：多对一（全部内网共用一个公网地址）、一对一定向转换（指定内网设备使用指定公网地址）。</p>
<p>后一种才是「多 IP 各走各的」的实现方式。配置时把内网地址与公网地址做成明确对应，避免动态分配导致出口漂移。漂移的后果是账号的网络身份在不知不觉中变了。</p>

<h2>第四层：验证</h2>
<p>四项验证。一，每个地址单独测试能否出网。二，每个地址的出口归属是否正确。三，返回路径是否正常（用需要双向通信的服务测试）。四，各地址之间是否互不干扰（改动一个不影响其他）。</p>
<p>第四项最容易被忽略。配置变更有时会影响已有地址的路由，导致原本正常的业务中断，而变更者以为只动了新加的那条。</p>

<h2>多 IP 的分配原则</h2>
<p>按隔离单元分配，不按账号数。一个需要独立网络身份的运营主体算一个单元。同一主体下的多个账号共用一条地址是合理的；不同主体共用则破坏隔离。</p>
<p>不要为了「用满」而硬塞。地址闲置的成本远低于隔离被破坏的成本。</p>

<h2>常见故障</h2>
<p>故障一，部分地址不通。多为掩码或路由缺失。故障二，能发出收不到。多为回程路径不对。故障三，时通时断。多为路由规则冲突或地址冲突。故障四，大文件失败。多为 MTU。</p>
<p>四类故障对应四层，按层次查比凭经验猜快得多。先接口、再路由、再转换、最后看应用。</p>

<h2>维护与固化</h2>
<p>固化三样：地址与用途的对应表、路由与转换的配置备份、变更记录。三样都不复杂，但缺了任何一样，半年后自己都看不懂当初怎么配的。</p>
<p>变更记录尤其重要。多 IP 环境下，一次小改动可能影响多条业务，有记录才能快速定位是哪次改动引入的。</p>

<p>多地址专线的配置难点不在加法，而在分流规则。建议先写出「哪台设备走哪个地址」的表，再动手配。没有这张表，配置会变成试错，而试错在专线环境里代价很高，因为每次改动都可能影响已经在跑的业务。</p>
<h2>常见问答</h2>
<h3>多个地址必须同段吗</h3>
<p>不必须。同段配置简单，分散段隔离更好。选择取决于业务对隔离的要求。</p>
<h3>能给多台设备各分一个吗</h3>
<p>可以，用一对一定向转换或独立接口。数量多了之后建议做映射表统一管理。</p>
<h3>需要专业设备吗</h3>
<p>简单场景普通路由器即可。涉及策略路由、多地址回程时，需要企业级设备或软路由。</p>
<h3>改配置要不要停机</h3>
<p>多数可热生效。改动前备份配置，出问题能快速回退。</p>
